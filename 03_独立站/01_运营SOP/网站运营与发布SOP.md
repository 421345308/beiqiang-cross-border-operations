# 网站运营与发布SOP

本页维护日常操作。网站源码与运行方法由独立源码仓库README和实际配置决定；搜索与收录按[搜索运营SOP](搜索与AI可发现性运营.md)，历史发布与测试查[证据记录](../02_开发记录/历史发布与验收记录.md)。旧版本的产品数、Sites版本、部署失败和测试计数不能成为当前基线。

## 按工作对象继续

| 工作 | 实际来源与完成条件 |
| --- | --- |
| 产品内容 | 产品中心及单款证据；源码中核字段、版本和映射，页面声明与实物保持一致 |
| 采购内容与询盘承接 | 当前指南/方案、表单和受控询盘存储；真实提交、通知、人工处理与CRM关联分别验证 |
| 报价、样品、订单协作 | 当前后台对象及买家权限；目标、确认能力、版本、决定与实际交易分开，网站按钮不代表收款或合同成立 |
| SEO与AI发现 | 固定窗口Search Console证据、URL检查及公开抓取；页面可访问、地图可解析、索引和AI引用分别判断 |
| 开发与部署 | 网站自身main、代码/测试、构建配置与正式域名；只改文档时核文档，不为完成表格虚造上线结果 |

## 产品需求与架构评估

每轮先按产品经理视角核真实买家路径、现有页面问题和相关公开网站，区分已观察事实、推断与待验证假设；外部页面记录来源和日期，不用设计观感推断销量。需求写清具体问题、买家收益、优先级和验收条件，回写现有产品与架构设计记录，不按聊天新建一套文档。

再按架构师视角核产品事实来源、数据模型、共享组件、多语言、稳定URL、性能、权限和发布风险。说明复用哪里、必要改动及暂不实现的边界；复杂度须对应实际需求与规模，不能为未来假设先建额外系统。确认可行后直接完成授权内开发，以正式页面和采购链路验收，不能只交需求文档。

上线后分别看使用故障、选款行为与有效询盘；样本不足时保留未知，不宣称转化提升。优先修复已证实的采购断点，再根据真实需求补图片、规格和产品。日常产品资产只保留原始素材与可用成品，旧批次、旧路径追溯放工作区外，当前使用界面与文件名统一贝强款号。

## 开发与发布

1. 在网站自己的main核未提交改动、远端及当前部署。只处理本任务范围，不把其他工作夹入提交。
2. 按具体改动查源码README与配置，运行必要测试、构建及受影响链路验证。不要从历史阶段说明复制命令、目录、环境变量值或旧测试数量。
3. 保留需求、实际差异、受影响功能和可核回执；通过后按已有授权提交推送main。Git推送、构建、平台部署和正式域名生效是不同结果。
4. 正式发布核版本与受影响页面、表单/通知或权限。失败先核实际部署阶段、域名、CDN和数据，不用备用站成功替代正式域名，不机械重建已完成能力。
5. 需要回滚时用经过核对的revert或平台原有成功版本，不重置未审查工作。当前结论回原开发对象；正式发布回执按版本留证。

## 为什么保留这些边界

网站承担采购发现、询盘与协作，正式付款/交易继续走已核Alibaba信保或双方合同；私密查询码和站内报价决定不是交易保障。曾出现源码、备用站与正式域名不同步，因此发布后必须核正式域名，不能按旧“全站已上线”概括。

首页供应商证明、产品选择与采购知识各回答不同买家问题。是否新增功能看能否减少真实采购断点；历史路线图里的阶段编号不是开发清单。跟进与客户事实仍回原CRM，网站不重建第二套客户经营档案。

境内不备案、服务海外买家的决定见本目录README；国内网络失败不直接证明代码或部署故障，也不能成为永不检查网络的免责条件。账号、私密查询码、客户上传、邮件和后台凭证保存在受控数据或既有配置中，公开记录只留脱敏证据。
