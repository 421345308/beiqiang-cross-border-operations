## 2. 独立站的工作原理

独立站由五层组成：

1. **源代码和素材**：保存在 `03_独立站/03_网站源码/`，包括页面文字、产品图、工厂图和询盘交互。
2. **构建**：把源代码整理成浏览器可以加载的正式网页文件。
3. **保存版本**：每次正式修改形成一个可追溯版本；有问题时可以对照旧版本排查。
4. **部署**：推送到 GitHub `main` 后，EdgeOne 自动拉取代码、构建静态文件并发布。
5. **域名与边缘层**：`www.beiqiang.online` 绑定到 EdgeOne，是唯一买家入口；旧 `chatgpt.site` 只作历史记录。

买家的实际路径是：

`Google / TikTok / LinkedIn / 邮件 / Alibaba → 独立站落地页 → 查看鞋款与工厂证据 → 选择款号 → WhatsApp / 邮箱 / Alibaba 发起询盘 → 样品与报价沟通`

## 3. 日常怎么操作

### 固定开发与发布流程（以后每次改站都照此执行）

1. **先定义销售目的**：写清本次改动要改善发现产品、建立信任、资格筛选、联系业务员、样品推进或复购中的哪一环，以及准备观察哪个指标。
2. **读取真实资料**：先读总档案、本 SOP、对应产品数据包和历史发布记录；材料、尺码、颜色、MOQ、价格、交期、包装、认证等没有证据时不写死。
3. **创建变更分支**：在本地仓库 `03_独立站/03_网站源码/` 使用 `codex/主题` 分支开发；正式生产分支保持为 GitHub `main`。
4. **开发与本地验证**：先用 `node --version` 确认 Node.js `>=22.13.0`，再修改 `app/` 和 `public/`；至少运行 `npm test` 与 `npm run edgeone:build`，并检查导出目录中首页和关键产品页存在。本机默认 Node 仍为 20.14.0 时必须切换到 Node 22，不能把 `node:fs/promises.glob` 缺失误判为代码故障。
5. **检查差异**：检查文案、图片、链接、联系方式、移动端、SEO、未确认承诺和 `git diff`，不得把密钥、原始客户资料或无关文件提交到仓库。
6. **提交和发布**：提交到 GitHub；合并或推送到 `main` 后由 EdgeOne 自动部署。当前小团队可直接更新 `main`，改动规模扩大后改为 Pull Request 审核。
   - 2026-08-23 用户已明确持续授权：独立站改动通过自动测试、EdgeOne 导出、ESLint 和差异检查后，Codex 可直接提交并推送 GitHub `main`，无需每次再次询问。该授权不取消正式域名验收、敏感信息检查和故障回滚门禁。
7. **双地址验收**：先检查 EdgeOne 本次临时部署地址，再检查 `https://www.beiqiang.online/`；至少验证首页、改动页、图片、WhatsApp、邮箱、Alibaba 链接和手机端首屏。
8. **记录结果**：在总档案或本 SOP 记录提交号、部署结果、页面变化、指标假设和待观察数据；只有真实浏览器验收通过才标记上线。
9. **回滚**：优先在 Git 中撤销问题提交并重新发布，或在 EdgeOne 选择前一个成功部署；不得用 `git reset --hard` 覆盖未确认的本地工作。

### 已知失败原因与防复发规则

- EdgeOne 曾把仓库根目录识别为 Next.js 并加载 `@edgeone/opennextjs-pages`，随后寻找静态站不需要的 `.next/required-server-files.json`，导致“网站已经导出但部署仍失败”。
- 解决办法是把 Root directory 指向 `edgeone-deploy`，让平台按纯静态项目执行适配脚本；不要随意删掉该目录或把 Root directory 改回仓库根目录。
- `nodejs_compat` 重复声明曾导致旧 Sites 发布失败；当前 EdgeOne 流程不依赖该旧配置。
- `npm audit` 当前报告依赖树存在 18 个问题（1 low、4 moderate、13 high）。这是独立的依赖治理任务；静态构建可用不等于可以忽略，但也不得直接运行 `npm audit fix --force` 破坏项目。

## 4. 当前网站能做什么、不能做什么

当前可以：

- 向买家说明贝强的产品方向和 B2B 合作方式。
- 展示 6 个代表款、产品与工厂照片，并提供 BQ001、BQ002、BQ009/L1026 三个可独立收录的产品页。
- 让买家选择款式并生成采购简报。
- 跳转 WhatsApp、业务邮箱和 Alibaba.com 店铺继续沟通。
- 被搜索引擎和外部研究工具读取。
- 保存合格询盘和来源事件，返回唯一参考号，并在 SMTP 配置有效时通知业务邮箱。
- 通过受保护的内部询盘台账查看记录、排除内部测试并导出 CSV。

当前还不能：

- 自动分配业务员、记录回复时间或推进样品/报价/订单阶段。
- 在站内直接修改询盘状态；当前 CSV 仍需进入销售跟进表继续管理。
- 为每个鞋款提供完整独立页；目前仅完成三个重点款。
- 自动发送产品目录、报价单或样品申请确认。
- 代替 Alibaba.com 的交易保障、订单和付款能力。

因此，现阶段独立站是“获客与筛选入口”，Alibaba.com 是“平台信任与交易承接”，WhatsApp/邮箱是“沟通与推进工具”。三者应互相导流，而不是互相替代。

## 7. 风险边界

- 不公开未确认的最终 FOB 价格、MOQ、交期、库存和产能。
- 不写医疗、矫形、治疗、防水、认证或品牌合作等无证据声明。
- 不使用与实物不一致的 AI 鞋款图。

## 8. 功能立项判断标准

任何新功能至少要改善以下一项，否则不进入近期开发：

1. 让目标买家更容易从搜索、内容或外联发现对应鞋款。
2. 让买家更快判断贝强是否适合其市场和采购方式。
3. 用真实产品、工厂、样品、质检或包装证据降低采购风险。
4. 收集足以报价和判断买家质量的信息。
5. 让业务员更快收到、分配、回复和跟进询盘。
6. 提高询盘到样品、样品到报价、报价到订单的推进率。

## 15. 2026-08-23 第九阶段：商业漏斗仪表盘

### 如何查看

1. 使用 `INQUIRY_ADMIN_TOKEN` 加载询盘后台后，仪表盘自动读取聚合数据。
2. 可切换 7、30、90 天；短周期用于检查近期改版和投放，长周期用于观察样品、报价和订单推进。

4. 仪表盘接口只返回汇总，不返回买家姓名、邮箱、消息正文或上传文件。

### 经营判断顺序

1. 浏览少：先检查获客渠道、搜索覆盖和落地页入口。
2. 浏览多但加入清单少：检查首图、款式匹配、已确认规格和 CTA。
3. 加清单多但询盘少：检查询盘字段负担、信任证据和联系替代方式。
4. 询盘多但 Qualified 少：检查渠道定向、买家公司和采购量质量。
5. Qualified 多但样品少：检查响应速度、样品条件、产品证据和未确认参数。
6. 报价多但接受少：复盘价格、贸易条款、MOQ、交期、包装和买家异议。
7. 接受报价但未成订单：核对 Trade Assurance/合同、付款条件和下一步到期日，不能把接受报价统计成订单。

### 数据边界

- 可选事件仅来自明确接受分析的访客，是次数而非独立人数，不能计算成完整站点流量。
- 询盘、报价与订单取自 Blob 业务记录；内部测试自动排除。
- `Qualified now` 等阶段是所选周期内收到询盘的当前状态，不是阶段在该周期发生的次数；后续如需精确阶段耗时，应增加不可覆盖的阶段变更日志。

### 为什么要拆分三种决策

旧界面把“拒绝”和“要求修改”放在同一个按钮及自由文本中，无法可靠区分仍有成交可能的谈判与真正拒绝。现在买家必须选择 `Accept as issued`、`Request changes` 或 `Decline quotation`，三种结果分别进入后续动作。

### 买家操作

2. 完全接受当前版本时点击 `Accept as issued`；这只记录商业接受，仍不是生产订单。

## 47. 2026-08-24 第四十一阶段：买家工作台运营漏斗

### 每周固定查看

### 诊断顺序

- 合格请求存在但SMTP发送失败：检查SMTP配置、授权码和发送日志；程序显示发送成功只代表SMTP已接受，不代表客户收件箱已收到。

- 已兑换但加载低：检查正式域名、EdgeOne函数、会话有效期和撤权状态。
- 已加载但摘要展开低：检查项目排序、最新买家说明、产品标识和行动文案是否能回答“客户现在应该做什么”。
- 摘要展开高但私密承接低：检查项目私密码交付、行动必要性和入口说明；不得为了提高点击制造虚假紧迫感。

## 48. 2026-08-24 第四十二阶段：数据保留、删除与买家文件安全

### 每周固定检查

1. 后台查看 `RETENTION HOLDS` 和 `DELETION WORKFLOWS`，逐条确认负责人和下一动作。
2. 检查已到期审查日期；到期只触发人工复核，不允许把到期理解成自动删除。

4. CSV留档时查看审查日期、冻结状态和删除状态，但不要把管理员或删除口令放入表格。

### 删除请求流程

1. 核验客户身份和代表公司提出请求的权限，记录原邮箱回复、已核验WhatsApp或其他可信依据。
2. 检查是否有订单、付款、争议、履约、索赔、安全调查或必须保存的正式记录；存在时先放置准确类别的冻结。
3. 无冻结且范围明确后，由申请人记录删除请求和原因。
4. 由不同的具名批准人使用独立删除口令，写明保留评估；有已确认订单时确认正式系统中的必要记录继续保留。
5. 等待至少24小时，期间可取消或新建冻结。冷静期结束后再次检查，输入 `DELETE 询盘参考号` 和执行依据。
6. 保存最小删除回执，检查计数；发生 `execution_failed` 时停止重试并调查日志、文件和询盘是否仍在。

### 文件安全流程

- 新买家上传一律默认隔离。网站只检查允许类型、大小和存储元数据，不包含病毒扫描。
- 隔离文件只下载到批准的隔离设备/扫描环境；页面确认和二进制强制下载只是降低误打开风险，不是扫描。
- 通过线下工具和人工内容核查后，填写工具/方法、日期和结果，再标记已审查；发现异常立即重新隔离并记录原因。
- “已审查”是内部操作状态，不得对客户承诺绝对无病毒；文件撤销、隔离和永久删除是三个不同动作。

### 权限与系统边界

- 普通管理员口令可查看记录、设置审查日期和冻结；批准及执行删除还要求独立的 `INQUIRY_DELETE_TOKEN`。
