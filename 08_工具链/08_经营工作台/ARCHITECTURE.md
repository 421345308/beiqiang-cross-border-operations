## 0.1 Agent Runtime 架构契约（2026-11-05）

工作台以 **Agent 为执行主体**：Agent 根据目标、可用能力和实际结果动态决定下一步；确定性操作及可复用步骤由业务服务提供，必要时组合成流程，但流程图不是运行时的前置中心，也不预设固定角色或固定步骤。以下为目标边界，实际代码和验收以 [README](README.md) 为准。

```text
负责人 / UI / 桌面 Agent
          ↓
Runtime：任务状态、运行尝试、执行后端、事件与恢复
          ↔ Orchestration：按目标委派、依赖、范围和汇总（渐进实现）
          ↓
Capability：发现与调用共用业务服务，服务负责校验及授权边界
          ↓
Data：原商品/客户/渠道/项目档案和素材；SQLite 存现有索引与任务状态
```

| 层 | 职责与边界 | 现状与增量方向 |
| --- | --- | --- |
| Runtime | 管理一次尝试的启动、观察、取消和恢复；记录明确状态与来源；不决定鞋款事实或商业承诺 | `agent_jobs.py` 仍负责状态、业务提示、成果写回和进程生命周期；Codex CLI 保留为执行后端，逐步抽出可测试的协议适配，不因接口抽象宣称其他模型已接入 |
| Orchestration | 按目标和需要创建子任务，声明输入版本、允许写入范围、依赖、预算和成果；主办汇总并检查冲突 | 不同对象可并行、同一服务内按对象限制；尚无工作台可见的父子任务、依赖图、细粒度写入协调或跨服务抢占 |
| Capability | 按对象及意图发现能力；结构化声明输入输出、版本、实际副作用、授权、连接状态与恢复方式；UI、MCP、CLI 调同一业务服务 | `desk_mcp.py` 的工具表和 `desk_cli.py capabilities list` 可查询静态 MCP 定义；对象过滤、连接状态和完整契约未统一，现有 hints 不是强制授权 |
| Data | 业务事实、原素材与外部回执留各自原处；已有 SQLite 保存任务、成果索引和画布，不复制商品库或 CRM | `agent_jobs` 与旧 `runs` 是分开的 JSON 行；`business_artifacts` 存成果索引、正文在原业务 `.local`；`creation_canvases` 以版本条件写入。SQLite 记录不自动构成跨进程调度或外部幂等保证 |

### 执行、协调与恢复边界

- 后端适配负责启动、将提供方事件映射成运行时事件、保留提供方会话/任务标识并处理取消；不得绕开既有环境、只读模式、模型配置及业务授权。新增后端要先证明能力、认证、成本和恢复语义，不通过统一类名暗示多模型已可用。
- Runtime 的任务、尝试、事件与成果引用应可跨重启读取；`queued / running / needs_input / completed / failed / cancelled` 反映运行事实，`completed` 只说明工作成果已存，不证明平台生效或经营目标达成。检查点必须绑定输入版本与副作用；本地取消不会撤销已提交、发信或扣费。
- Agent 自行决定是否拆分；每个委派明确主办、对象、读写范围、输入版本和资源上限，子任务只共享必要上下文和成果引用。用业务服务的原子版本校验与短事务保护相同资源，外部调用结果不明时先查回执。不能把模型内子 Agent 或单进程互斥写成完整协调机制。
- 运行轨迹与资源用量按实际返回的数据记录：任务、尝试、会话、时间、状态、可安全展示的工具事件、成果及可得 token；无数据与零区分。估算费用、实际账单和未知费用分开，不将私有原始日志或客户资料提交公开仓库。

### 能力、上下文与业务写入

`business.py`、`business_context.py`、`creation_canvas.py`、`product_creation.py`、渠道及客户服务继续作为业务能力来源；`server.py`、`desk_mcp.py`、`desk_cli.py` 是入口而非平行事实库。对象及关联原档按需读取，保留时效、范围与来源。核心动作需要共享服务验证，而不是依赖 UI 文案或提示词；现有独立插件和 CLI 不自动纳入工作台门禁。

2026-11-05 已修复一类可复现的客户商机陈旧写入：`customer_commercial.py` 的 revision 现在同时覆盖商机数据与持久化 workflow 状态；MCP 新增只读 `get_customer_commercial`，`save_customer_commercial` 必须携带 Agent 实际读取到的 revision，不再在写入前替 Agent 重取最新版本。冲突返回版本冲突，要求重新读取和合并。回归测试覆盖 Agent 读取后人工修改，以及下一步变化使旧 revision 失效。

此修复阻止了该 MCP 调用路径静默覆盖较新的同进程编辑，但不等于完整并发保护：`customer_workspace.py` 的派生 JSON 文件仍依赖进程内 `app.lock`，独立工作台进程之间的文件写入协调尚未验证；其他客户分析/工作流写入口也需纳入统一版本边界。下一步应先完成跨进程一致性设计与交错写入测试，再推广到其他客户派生资料。客户外发规则不因此改变。

参考 [OpenAI Agents SDK 运行循环](https://developers.openai.com/api/docs/guides/agents/running-agents)及[委派与交接](https://developers.openai.com/api/docs/guides/agents/orchestration)：区分模型与工具的连续交互、会话延续，以及主办委派后仍负责整合。参考 [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)和[容错](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)：区分执行检查点与长期事实，未收到外部回执时保持结果未知。它们是边界设计参考；本项目未因本次评估引入任一框架或自动继承其功能。

## 1. 核心架构决定

工作台不是“给人工后台加一个聊天框”，而是人与 Agent 共用的经营执行系统。负责人给目标，Agent 能发现能力、取得上下文、执行、检查结果、回写并提出下一步；人工可以查看、修改和接管同一业务对象。

1. **同一业务动作只实现一次。** UI、MCP、CLI 调用同一业务服务，共用校验、授权判断、版本控制和结果回写。不允许页面能操作、Agent 却只能写操作建议。
2. **能力优先于说明文档。** 固定的数据处理和平台动作写成可执行工具；可复用流程写成执行逻辑；Skill/SOP 只保留专业方法、业务约定和例外处理，不让 Agent 每次读长文再手工重演。
3. **确定性程序与 Agent 判断分工。** 程序负责取数、转码、保存、提交、回读及状态管理；Agent 负责选题、判断、规划和取舍。流程可组合，但不把经营决策硬编码成固定顺序。
4. **增量演进。** 复用当前本地服务、SQLite、对象身份、素材目录和执行器；不预先引入微服务、大型编排框架、新 CRM 或重复知识系统。
5. **成果而非工具数量驱动。** 每次改造都对应真实业务旅程，证明减少了重复解释、搬运、等待和返工。

业务资源安排沿 PRODUCT 的现行方向；这里不另设业务线排名，也不要求所有工作在同一轮完成。

## 2. 统一业务能力层

### 2.1 从现有实现提取服务

先检查现有 `business.py`、`desk_mcp.py`、`desk_cli.py`、`agent_jobs.py`、`business_context.py`、渠道修改、客户工作区、素材和创作模块。按实际代码复用，不因文件名相近就假定功能已完成。

调用关系为：

```text
UI / MCP / CLI
        ↓
共用业务服务：对象读取、业务校验、修改、任务与成果
        ↓
已有渠道连接器 / 图像视频工具 / 数据处理工具
        ↓
原业务数据、素材、正式回执与经营结果
```

先让已有关键操作对 Agent 可用，再扩新能力。已有官方 API 或项目客户端可以完成的动作，不退回浏览器点击；无接口但可正常操作的场景使用现有浏览器能力。没有可用入口时返回具体缺口及可继续完成的部分，不伪造成功。

### 2.2 能力发现与调用契约

提供轻量能力发现入口，可以先由现有工具定义生成，不先造插件市场。Agent 按任务与业务对象查询能力，而非每轮注入全部工具。

| 契约 | 要求 |
| --- | --- |
| 身份与用途 | 稳定名称、接口版本、适用对象、解决的业务问题 |
| 输入输出 | 结构化参数与结果；引用既有对象 ID、素材 ID、任务 ID，不要求人反复提供内部路径 |
| 可用性 | 当前连接、权限、额度与最近验证状态；未知与不可用分开 |
| 副作用 | 只读、本地可恢复修改、外部提交、付费等实际性质 |
| 授权与成本 | 适用的既有授权、是否需本次确认；估算与实际费用分开，未知费用不编造 |
| 执行结果 | 状态、对象版本、成果引用、外部回执、时间及失败原因 |
| 恢复方式 | 是否可安全重试、如何查外部状态、是否可局部接续 |

短操作返回结构化结果；长操作返回任务标识，支持查询、取消和接续。不把所有工具结果包装成 Markdown。错误应区分参数问题、权限不足、断连、额度不足、版本冲突及外部结果不明，便于 Agent 选择下一动作。

以下是应逐步覆盖的能力域，不是已经存在的 API 名称，也不是要求每个动作创建一个新接口：

- 商品与供货：查找、读取当前事实、匹配款式、读取素材、更新原档并保留版本。
- 渠道商品：读取正式状态、准备差异、校验、按授权提交、查询审核、回读生效内容。
- 内容：参考案例、选题、脚本、分镜、素材编辑、图像/视频任务、剪辑交付、版本评审。
- 客户：企业研究、往来读取、商品匹配、资料包、邮件审核材料、商机与下一动作。
- 数据：按对象和时间窗取数、保留口径、比较版本、归纳异常及反馈。
- 执行：能力查询、任务委派、步骤状态、成果检索、接续和同步结果。

跨对象的业务操作应能够一次调用完成合理范围的工作，例如“为指定客户组合现有三款鞋的资料包”；不要迫使 Agent 模拟几十次页面点击。

### 2.3 人工操作与 Agent 操作对等

关键业务动作至少应当有一个稳定、可测试的程序入口。并非每个 UI 按钮都需要单独暴露成工具，但不能存在长期只能靠人工页面操作完成的核心业务链路。

Agent 生成的结构化分镜必须能进入现有画布；人工修改标题、图片顺序或脚本后，Agent 读到的是同一版本。界面不只是查看 Agent 的聊天记录，而是能够操作真正的成果。

## 3. 按需复用的执行逻辑与任务恢复

### 3.1 流程是 Agent 可选择的执行逻辑

围绕真实任务实现可复用函数或步骤定义，不先开发通用拖拽编排器。可复用流程有输入、输出、版本、必要依赖和完成条件；Agent 可以自行选择能力、分支、并行委派或跳过不必要步骤，而不是每次按固定流程执行。

例如，主图已有可用实拍时不强制重新生图；已有合格客户研究时不重新全网调查；一个镜头失败时不重做整条视频。

在已有任务与成果体系中按需扩展：业务目标、对象引用、父子任务、依赖、执行者、步骤输入版本、结果引用、外部任务标识、下一动作及耗费。字段能复用就复用，不机械创建新实体或第二份状态库。

支持从经营目标发起任务，不局限于“必须先点开某款商品才能委托”。跨对象任务应关联其实际处理的商品、渠道及内容，成果仍归原业务对象，不新建第二套事实源。

### 3.2 持久化与恢复语义

任务至少能区分排队、运行、等待依赖或审核、部分完成、完成、失败和取消，具体枚举可沿用现有实现。不能把保存了总结当成业务完成，也不能在没有进程或调度器运行时显示“持续经营中”。

- 长任务在关键步骤保存检查点。会话 ID 帮助恢复上下文，但不能代替业务状态与产物记录。
- 复用已完成步骤前，检查输入商品、素材、规则及版本是否变化；只让受影响的下游结果失效。
- 服务重启先核原进程、外部任务和已落盘成果，避免双重执行。取消只停止后续工作，不声称撤销已经发生的提交或扣费。
- 读取和可恢复的内部处理可采用有限重试；无效输入、权限拒绝和余额不足不能无限重试。
- 邮件发送、商品发布、付费生成遇到超时或结果不明，先查外部回执。平台支持幂等键时使用；不支持时保留请求标识并核实，不能假设本地去重就能保证外部“恰好一次”。
- 恢复某一步不要求负责人重新解释全项目，只暴露真正缺失的授权或资料。

### 3.3 授权进入执行链路

普通研究、内部资料与代码修改、测试及已有授权内的业务动作直接执行。审批只放在确需确认的边界，不给每个步骤增加一道人工确认。

客户开发邮件仍绑定具体收件人、主题、正文和实际附件审核；实质修改后只使相关审核失效。付费 AI 视频生成沿当前明确确认要求，不能把“建设内容流程”当成费用授权。已有获准的平台修改不因接入工作台而重新要求重复授权。

关键外部动作的校验应进入共用业务服务，让 UI 和 Agent 一致；不能仅靠前端按钮或提示词宣称已形成强制权限控制。对于继承的独立插件或命令，明确实际控制范围，不声称它们天然受工作台门禁覆盖，也不因此禁用全部普通任务能力。

## 4. 多 Agent 并行与写入协调

按独立交付物分工，不固定启动一组常驻角色。单 Agent 能直接完成的小任务不强行拆分；跨渠道研究、独立镜头制作、代码与验收可在条件合适时并行。

每个子任务交代：目标、输入对象与版本、允许修改的对象或文件、预期成果、依赖和资源上限。共享必要业务资料与成果引用，不转发全部聊天、无关客户资料或凭证。

**读可以共享，写需要明确范围。** 并发粒度尽量到渠道链接、素材或文件，而不是把整款商品全部锁住。例如，国际站标题与抖店视频可以并行准备，但不能同时覆盖同一个主图集。

复用现有任务记录维护主办与写入范围；优先采用原服务版本校验和短事务等适合当前实现的办法。冲突时重新读取并合并，不用最后写入覆盖前人的修改。Git 提交和推送串行，精确包含本任务文件；不要把其他 Agent 的暂存改动一起提交。

本地手动 CLI、桌面会话或跨机器执行者未接入协调机制时，明确其覆盖缺口；同进程锁不等于跨进程保护。不为尚未遇到的问题先建设分布式锁平台。

主办负责整合与验收。关键内容、复杂变更可请独立 Agent 复核；不同模型或角色的意见一致也不是事实证据。子任务应交付可读取的素材、数据、补丁或业务记录，而不只是各写一份报告。

针对外部模型额度、平台速率限制和本机资源配置并发上限。达到上限时排队，不盲目扩 Agent 数量。并行收益应看实际耗时、成本和质量，不能以启动数量评价。

## 5. 上下文、事实与经验复用

按任务读取当前目标、负责人决定、对象原档、渠道状态、既有成果和必要专业方法。来源时间、适用范围和冲突保留；文件更新时间不自动等于业务事实更新。

- 对象查询和关联资料是主入口，按需分页展开，不默认把全仓库注入每次调用。
- 商品事实与营销表达分开；原始素材不被生成图覆盖；内部供货信息与对外展示按根规则处理。
- 已确认能力直接复用，不能因为当前预览未出现某字段就要求负责人重新确认全部信息。
- 重要决策及实际结果写回对应业务源，进度沿既有任务记录；不靠聊天摘要维持经营状态。
- 经验保存适用商品、渠道、模型版本、样本和结果。一次成功不升级为普遍规则；进入项目记忆仍按现行确认协议。
- 经过重复使用验证的流程改进进入代码、配置或模板；保留版本与回退，不自动覆盖稳定方案。

不要求为每个 SKU 新写一份生图 Skill、为每种任务维护一份长 SOP。只有专业判断确实不可由通用接口与业务数据表达时，才补充必要说明。

## 6. 内容生产：重点打造的可调用流程

### 6.1 案例研究不是收藏链接

Agent 能从现有案例或可正常访问的公开内容中提取参考，并关联商品及内容目标。记录来源、观察日期、可见数据、目标人群、开头、画面节奏、产品露出、字幕和可迁移方法。

明确区分“画面观察”“效果数据”“制作方式推断”。别人没有公开工作流时，只提出可以复现相似表达的制作方案，不能声称掌握其真实工具链；播放量与点赞不能冒充销量。

学结构和表达，不复制无授权品牌素材，不伪造真实买家评价、购买经历、工厂记录或产品性能实验。研究结果必须进入一次实际制作验证，而不是不断扩充案例库。

### 6.2 图文生产

流程：商品与已有素材 → 用户需求与参考 → 选题及封面方向 → 逐张画面和文案 → 生图/编辑/排版 → 商品保真与文字检查 → 整组预览 → 发布准备或已授权发布 → 结果回收。

每组图文有一个清楚的表达目标，逐张图片承担不同作用，不把几张产品参数海报拼成内容。上脚、穿搭、生活场景、产品细节按实际主题选择；换背景和换标题不算新的内容策略。

Agent 可逐张修订并复用其他图片。精确规格、尺码表与重要文字优先用可校验的排版处理，不能信任模型直接生成的小字。成果包括可打开的图片、文案和关联信息，不止提示词。

### 6.3 短视频生产

流程：商品与用户目标 → 案例研究 → 简明脚本 → 分镜 → 权威商品参考与人物/场景资产 → 分镜生成或实拍素材选取 → 片段筛选 → 剪辑、字幕和音频 → 成片检查 → 发布包 → 数据复盘。

镜头明确时长、画面重点、产品展示、动作、声音及所需参考。优先自然可信的表达，不靠冗长提示词、复杂运镜和夸张表演掩盖产品价值。允许实拍、AI 与混合制作，模型不是每个镜头的必选项。

通过当前可用工具验证 GPT 生图、Seedance 或其他模型的版本、参考输入、尺寸、时长、费用和输出能力；不把某个版本限制写死为所有模型规则。已购产品或网页可使用，不代表本地 Agent 已有可调用接口。无直接调用能力时接现有可用工具及标准交接包，准确标记尚未自动化的一步，不把输出提示词报为生成成功。

保留参考图角色、生成参数、模型版本、任务 ID、候选片段、采用版本及编辑关系。支持局部重生成和镜头替换；人工改分镜后 Agent 读取新版本继续，不重跑全片。

剪辑优先调用已有合适工具，完成片段拼接、节奏、字幕、口播、音乐、封面及平台版本导出；不为了系统完整自行开发一个完整剪辑器。音乐、配音、参考人物和其他素材保留适用使用依据。

### 6.4 质量、耗费与交付

检查鞋面结构、鞋底轮廓、配色、左右脚和数量、上脚比例、帧间一致性、文字、音画节奏及实际卖点。自动视觉检查是辅助筛查，不能声称已绝对保证商品一致性。严重变形必须返工或改用更可靠素材。

生成数量、并发数、尝试次数与费用遵循已批准范围，失败有停止条件。没有成本数据就标未知，不无限重抽。权限或费用阻塞时继续完成不受影响的策划、剪辑准备和已有素材处理。

每项成果带商品、渠道、脚本/分镜、素材版本、审核及发布状态；成片可播放，图文可整组预览，用户可修改，Agent 可再读。发布包与已发布内容明确分开。

## 7. 业务工作流样板与最小交付

以下定义目标输入输出，不替代各渠道现行 SOP，也不强制固定步数。实施时核实际接口、平台规则与授权，已接通的能力直接复用。

| 样板 | 核心执行链 | 可验收成果 |
| --- | --- | --- |
| 国际站商品经营 | 实款与链接 → 商品池/关键词/类目属性/图文及数据诊断 → 有依据的优化差异 → 素材生产 → 按授权提交 → 审核及正式回读 → 效果观察 | 可用标题、主图/详情素材与修改记录，关联实际链接；明确准备、已提交、已生效及公开核验状态 |
| 抖店商品经营 | 店铺与实际商品 → 商品卡、标题、SKU、主图、详情、选码和价格承接分析 → 候选制作 → 校验与授权提交 → 状态回收 | 适合手机消费者的可编辑商品方案和素材；按店铺保留独立价格、库存及履约信息 |
| 抖店图文 | 商品及案例 → 内容主题 → 逐图设计 → 生成与排版 → 检查 → 发布包/发布 → 复盘 | 可预览图片组、封面、标题、正文及对应商品，不以模板数量验收 |
| 短视频 | 商品及案例 → 脚本/分镜 → 参考资产 → 生成/实拍 → 剪辑 → 成片质检 → 发布包/发布 → 复盘 | 可播放成片、封面和可继续编辑的制作资料；生成、剪辑和发布状态分别记录 |
| 客户开发 | 既有候选 → 企业与采购匹配 → 选款 → 中英文材料及附件 → 逐封审核 → 授权发送 → 反馈与商机接续 | 同一客户内可审阅的完整材料、联系依据和下一动作；历史进口不等于当前意向 |
| 独立站运营 | 正式页面/商品与实际搜索询盘 → 问题定位 → 内容或代码差异 → 测试/发布 → 正式页面验证 → 询盘效果 | 关联源码提交、发布版本和实际页面；构建成功不等于已上线 |

国际站完整运营范围还包括供货核实、有效商品覆盖、店铺展示、商品质量及询盘接续；抖店包括商品卡、图文、视频、成交和退换反馈。无需为每项建设独立菜单，按现有对象组织。

对当前已启用的平台自动优化，不能仅因字段不同于旧快照就还原；先判断是否影响产品事实或本次目标。评分、关键词量、模型限制与平台规范按实际最新口径读取，不伪造实时数据。

## 8. UI、运行反馈与经营数据

UI 与 Agent 操作同一对象和版本。人改文字、换素材、选镜头或调整下一步后，Agent 接续应读到这些变化；轮询不能覆盖未保存编辑。

总览显示真实在办事项、已有成果、等待原因、失败后的可执行动作及少量有证据的建议。不用固定百分比模拟进度，不把工具日志堆给负责人；诊断日志保留在适当的内部位置。

每次重要业务动作关联执行前状态、变更、时间、版本、外部回执和观察窗口。数据至少说明来源、统计期、更新时间、单位及覆盖范围。缺失不是零，历史快照不是实时数据。

分别衡量：

- 生产效率：人工介入次数、返工、有效素材产出、真实耗时及费用。
- 平台表现：按实际可取口径观察曝光、点击、访问、询盘或成交。
- 经营质量：有效采购讨论、样品/订单推进，或国内成交、退换及贡献利润。

不同渠道、店铺、付费/自然流量和统计窗口不混算。没有稳定归因时明确限制，不能把修改后的上涨直接认定为修改导致。AI 建议包含证据、假设和可执行动作，不只输出总结。

事件触发及定时运行复用现有任务机制，按已获授权范围设置，考虑去重、冷却和资源上限。没有运行进程、调度或机器在线条件时，不声称无人值守持续执行。

## 9. GitHub 与跨 AI 接续

继续使用现有运营及独立站仓库，各自按项目规则维护 `main`。公开代码、接口契约、方法及脱敏阶段结果可同步；客户原件、联系方式、订单隐私、内部敏感商业数据和凭证不进入公开仓库。

重要阶段完成后，在原业务入口写清目标、实际结果、依据、未完成项和下一动作；记录对应提交及同步失败原因。先核提交范围，推送后核远端，不把只提交本地报为已同步。

不要求把全部运行日志和媒体塞进 Git，不为每轮生成新的日报/交接文档。客户和素材在受控存储，跨机器访问及恢复以实际验证为准；公开架构文档不是私有业务数据的替代品。

## 10. 实施顺序与验收契约

### 10.1 每轮交付一个可使用的增量

1. 核现有实现、业务需求和真实权限，在已有入口说明已可用、部分可用与本轮缺口；不另做庞大的审计工程。
2. 选一个真实经营样板，复用已有服务，把最缺的动作开放给 Agent，并让 UI 使用相同结果。
3. 同时补该动作所需的恢复、版本与回执处理，不为了完整抽象预建全部能力。
4. 跑必要测试并在真实业务中验收；阻塞只影响相关步骤，独立工作继续。
5. 回写实际能力与结果，按规则同步，再用发现决定下一项。

允许不同执行者并行推进独立样板，不要求等全部底层框架完成才生产内容或运营商品。也不能以业务紧急为由长期保留 UI 与 Agent 两套实现。

### 10.2 技术与体验验收

- **能力一致：** 同一个业务动作经 UI 与 Agent 调用，保存到同一来源，版本与校验一致。
- **成果接续：** Agent A 产出方案，用户在页面修改，Agent B 直接读取修改继续；不需要复制聊天和提示词。
- **并行：** 独立对象可同时推进；冲突写入被发现且能接续，不覆盖其他人的文件。
- **恢复：** 在真实可控制的内部步骤中断后继续，复用有效成果；外部提交超时通过回执核实，不重复发信、发布或扣费。
- **内容交付：** 有真实图片组或可播放成片及编辑资料；只生成脚本或提示词时明确标为相应阶段。
- **授权：** 已授权普通动作不重复审批；应审核的外部动作不绕过原规则。
- **同步：** 另一个有权限的 Agent 能从仓库和相应业务入口理解目标、实际结果及下一步；未共享私有资料的部分准确标明。

### 10.3 效果与边界

技术测试通过、业务流程走通和经营效果改善分别报告。模拟接口只能证明模拟范围；本轮无客户反馈或发布数据时，不要求虚构成交来验收。

用可比任务记录人工介入、执行耗费、返工与质量，逐轮观察是否减少。未发生的经营收益不做承诺。

**完成标准：负责人交代目标后，Agent 可以发现并调用现有能力，合理分工，交付可用结果；人能看见、修改和接管，下一位 Agent 能继续。不是多写一套文档，也不是多增加几个菜单。**
