# 贝强本地经营与创作工作台：产品方案

**云端化目标（2026-11-10）：** 云端经营工作台成为负责人查看询盘、任务和结果的统一入口；既有新加坡服务器承担可安全常驻的云任务，本机继续承接本地素材、浏览器和渠道客户端。客户、商品及任务沿原业务对象接续，不建立互相竞争的事实来源；Agent 生成方案不等于已发信、完成交易或回写本地。按询盘可见、通知与安全，再到任务运行和协作的顺序增量交付。实际运行状态见 [README.md](README.md)。

**Agent 原生产品体验（2026-11-05）：** 负责人给出经营或创作目标后，Agent 应能按需寻找资料与可用能力、判断下一步、在合适时委派并行工作，交付可查看、修改和接续的成果；负责人可随时接管。固定流程是可复用选项，不是每项任务的强制入口。运行架构见 [ARCHITECTURE.md](ARCHITECTURE.md)，当前实现与限制见 [README.md](README.md)。

## 稳定能力：任务接续与当前意图

**能力契约 `task-continuity-current-intent`（现行，2026-11-11）：** 同一任务换执行轮次或会话时，Agent 应能从任务摘要获取当前目标、已登记的有效决定及来源、下一步、成果位置和适用原档，不把最初委托或已被替代的决定当成现行目标。目标或决定可有明确理由地更新；更新后旧运行成果不能自动覆盖当前安排，应保留供复核。旧任务和会话仍能接续，未登记决定不等于没有约束。

改动此能力时，按[总控工作流](../../00_总控台/AGENTS.md)核对本契约，并运行 `tests_intent_summary`、`tests_intent_jobs`、`tests_intent_failure_race`、`tests_task_continuity`、`tests_task_workspace` 和相关接口及前端回归；检查领取、旧版本冲突、成果复核、当前目标显示与旧任务兼容。改变或替代此能力须在本节明确理由、替代方案和受影响验收，不以保留原实现为目标。隔离测试与现场可用性分别记录，当前实现和证据见[运行说明](README.md)。

## 稳定能力：回合验收与安全接续

**能力契约 `task-completion-followup`（现行，2026-11-11）：** 同一任务的一个执行轮次结束后，应保留可追溯的待验收事项，依据当前有效目标、能力、成果和实际证据决定已验完成、继续、需负责人决定、阻塞或结果未知；回合结束本身不等于整个经营目标完成。重复完成事件不能重复派工；目标或决定变化后，旧验收必须重新核对。已具备授权与执行条件的接续应有实际请求和可对账回执，结果不明时先核对，不盲目重发；未接通通知时只显示待处理，不冒充已提醒。

本轮代码仅对工作台内部的现有 AgentJobs 接入完成登记与验收；调用方仍须提交结构化结论及证据，系统不凭回合状态自动判定经营成果。符合既有检查的标准 `CodexBackend`、`mail_draft` 任务可在登记继续后自动接续原任务；其执行工具只读，最终可能保存内部草稿，不发送客户消息。其他任务保留明确下一动作并沿原入口处理。具体实现、隔离证据、未接入的外部会话与现场状态见[运行说明](README.md)。

更改此能力时须检查 `tests_completion_followup`、`tests_completion_dispatch`、`tests_completion_http_integration` 及总览/前端相关回归，覆盖重复事件、未达目标、意图变化、派工回执不明与对账；改变或替代契约应说明理由和验收，不以测试通过推断正式环境可用。

## 本轮实际交付与产品边界（2026-11-10）

第一阶段新增统一任务入口、明确对象的一句话路由、同一任务的多会话/多尝试轨迹与当前上下文接续。继续复用原任务、业务对象、成果和云队列，不另建看板事实库。用户先从 `/tasks` 找到工作，再打开任务详情或原业务对象，不必先找到某个聊天标题。歧义由负责人选择，计划保存与实际启动分开。

任务内的当前目标与显式登记的决定可随原任务版本调整；跨任务、跨业务的 Goal 和 Decision 仍以现行业务原档为准，尚未成为可独立编辑的通用实体。Command 暂不自动规划新项目或任意跨业务委派。本机执行器配置为 Sol，关联外部 ChatGPT 聊天仅供追溯。七项真实场景、生产上线、经营效果及人工成本指标不得由隔离测试代替，具体实现、已验证结果及下一轮范围见 [README](README.md#ai-原生任务入口第一阶段增量2026-11-10)。

## 2026-11-04 全渠道 V1.0 方向

负责人本次明确：海外 B2B 客户开发与订单转化、国际站、抖店、内容创作四条业务线同等重要，独立站与之协同。按真实截止时间、经营机会、潜在收益和成本动态安排，不预设业务线先后。下方旧版顺序与此冲突时以本段为准；各项实际能力以 README 和业务原档为准。

工作台沿现有商品中心、客户记录、渠道工具和统一 Agent 执行器建设经营闭环：发现机会、研究、制定策略、制作素材、执行、观察真实结果并迭代。导航目标为经营总览、商品中心、外贸客户、国际站运营、抖店运营、内容创作中心、独立站运营、数据分析及资产与工具；这是目标结构，现有五个主入口并不等于已完成迁移。

国际站诊断应围绕实际可取的商品、质量、流量、询盘和订单证据识别瓶颈，区分问题、原因假设与行动；负责人现行质量分要求不低于 5.0，平台口径变化时先核实。抖店、内容和客户各有独立经营目标和完整流程；搜索和独立站数据依据实际连接情况展示。历史指标注明时间，不作为当前表现或改动效果。

以真实商品及渠道身份接通为基础，逐条业务线验证可执行的闭环；不另建商品库、CRM或重复执行器。公开采购顾问和支付按后续优先级处理，不能以此阻塞询盘和云执行能力。

## 产品要承担什么

让负责人在本地集中管理生意与创作：知道值得做什么，找到真实资料，把工作交给Agent，直接使用成果，并看到后续结果。成功在于减少查找、重复说明、搬运结果和手工跟踪，让客户、商品和作品持续向前。

完整流程是：**发现机会或问题 → 选定目标与下一动作 → 人和Agent执行 → 成果回到对应业务 → 根据结果继续。** 国际B2B、国内零售和独立创作共用资料与执行能力，各有自己的目标与流程。

负责人于2026-11-02要求各业务流程最终都能整合到工作台接续，页面优先显示决策与行动所需的重要内容，细节和依据按需查看。按实际业务逐段打通，不把未连接的数据源包装成已经自动接入：同行找客户已可从已核国际站店铺进入原客户研究；付费海关数据连接待取得真实服务及权限后再确定。

## 经营系统方向（2026-11-03）

负责人希望工作台具备类似ERP的集中管理能力，并将市场趋势和渠道数据用于分析、改进独立站与国际站。目标是让商品、客户、渠道与订单围绕同一笔生意协同，形成“数据 → 发现问题或机会 → 明确改动 → 执行 → 观察结果”的循环；不以堆砌模块或照搬传统ERP为目标。当前仍以本地工作台为入口，实际接通的能力和数据更新时间以[README](README.md)为准。

| 经营能力 | 应解决的问题 | 接续方式 |
| --- | --- | --- |
| 经营总览 | 现在最值得处理哪些客户、商品及经营问题 | 汇总真实异常与下一动作，直达对应对象；已完成、待处理和等待结果分开 |
| 商品与供货 | 哪些鞋可供、渠道各自如何展示、修改后效果如何 | 同一商品关联实际供货、素材、各平台链接及商业条件；不同链接分别看数据和修改结果 |
| 客户与订单 | 谁在采购、下一步做什么、从询盘如何走到订单及交付 | 沿客户记录关联往来、报价、样品、订单和履约；按现有业务数据逐步接通 |
| 渠道与市场 | 客户如何找到我们、哪些页面或商品需要改进 | 联合国际站经营数据、网站搜索及询盘、市场趋势；按国家、渠道、时间窗查看，并指向具体页面或商品 |
| 执行与复盘 | 分析如何真正变成工作并验证是否有效 | 在原商品或渠道准备标题、图片、详情等方案；按既有授权执行并回读，记录变更日期，再比较可比期间的结果 |

数据优先使用已有的一手经营结果：国际站按正式商品链接ID关联曝光、点击、询盘和订单；网站按搜索词、落地页、流量与有效询盘分析；市场趋势用于发现需求方向，不代替真实采购反馈。不同渠道、国家、统计时间和商品版本分开比较；页面要告诉负责人该做什么，来源与原始数据按需查看。数据不足时给出可做的下一步，不伪造指标或把旧数当实时数。

接入顺序按业务价值和可用权限推进：先用已有国际站逐链接经营报表和网站询盘，再核实账号权限并接入Search Console及网站统计，随后补Google Trends和其他适合的数据源；具体自动刷新频率以真实接口能力为准。Google Trends [官方API](https://developers.google.com/search/apis/trends)目前须申请Alpha测试资格，可先使用[官方CSV导出](https://support.google.com/trends/answer/4365538)；网页指数是相对搜索兴趣，不是搜索量，不同查询设置不可直接拼接比较。未取得接口或数据时，不宣称已自动更新。

### 经营分析与Agent能力：研究建议（2026-11-03）

优先利用已授权国际站商品、图片、视频和订单接口；数据管家自然流量接口此前实测权限不足，不能把商品API等同于流量API。独立站采用[Search Console](https://developers.google.com/webmaster-tools/v1/searchanalytics/query)观察查询、页面和国家，[GA4](https://developers.google.com/analytics/devguides/reporting/data/v1/basics)在已有账号权限和实际事件采集的基础上分析访问到询盘。市场研究可用[UN Comtrade](https://uncomtrade.org/docs/un-comtrade-api/)比较国家和鞋类HS统计（不提供买家名单），[TikTok Creative Center](https://ads.tiktok.com/resources/help/article/creative-center)研究公开创意和趋势；Google Places有计费和使用限制，亚马逊SP-API以授权店铺为前提。国际站询盘与聊天、抖店接入仍按负责人决定暂缓。免费优先，申请与付费按实际需求和授权处理。

Agent工作时由现有产品中心、最新负责人决定、客户往来、渠道正式记录及当前任务生成面向对象的上下文：当前目标、有效事实、历史约定、数据时间和下一动作。保留各业务唯一事实源，不创建另一套人工维护的知识库；旧摘要与最新业务源冲突时先更新原入口。界面、桌面Agent和既有官方客户端逐步共用能实际调用的业务动作：查商品与客户、研究买家、生成选款与报价、准备渠道字段和素材、按已有授权提交、回读并回写。将已有国际站商品/图库/视频能力接入工作流，不从零重复开发；各动作的实际范围以应用README为准。

优先交付三个贯通案例：①真实客户往来→需求判断→匹配商品→可审核的报价及附件→记录结果与下一步；②某条国际站商品链接→当前图文及经营表现→生成具体修改→按既有授权执行与回读→在可比期间观察效果；③独立站搜索词和落地页→匹配商品与目标买家→提出页面改进并比较有效询盘。借鉴[Pipedrive的下一行动](https://support.pipedrive.com/en/article/activities)、[ERPNext销售单据关联](https://docs.frappe.io/erpnext/selling)及[Akeneo的渠道化商品信息](https://help.akeneo.com/v7-your-first-steps-with-akeneo/v7-understand-product-completeness)，以有效采购讨论、样品、订单和贡献利润判断成效，而非以接口数量和生成报告数量判断完成。

旧版问题不只是外观：菜单按工具划分；资料与业务对象脱节；任务主要从Markdown表格抽取；Agent限定为单篇原文的精确替换提案；画布和平台动作另走按钮。第一包已用对象内任务和共用业务读取替代默认入口；渠道执行及创作尚待继续贯通。

## 整体工作空间

主导航使用“总览、商品、客户、渠道、创作、客户资料包”。客户资料包只组织可发送的通用材料与客户专属材料，原件留在原处；商品和客户档案仍各自维护，不再复制成另一套资料库。跨业务工作列表从总览进入；每个业务页面都可调用Agent；工具连接和技术日志放设置。导航表达用户经营的东西，不表达后台有哪些接口。

| 入口 | 用户要解决的问题 | 页面与实际动作 | 结果如何接续 |
| --- | --- | --- | --- |
| 总览 | 当前目标是什么、先做什么、谁在推进、需要我决定什么？ | 当前重点、待推进机会、进行中的工作、需要处理的事项与新成果；按影响和真实时限排序，可调整优先级与负责人 | 每项直达原客户、商品、店铺或作品；长期方向引用总控，不在每页重复愿景 |
| 商品 | 有哪些真实可供款、能承诺什么、如何适配买家和店铺？ | 图片优先的查款与筛选；一款内看来源、规格、素材及渠道链接；组合选款单/目录，准备完整商品修改 | 共用产品事实与渠道商品分开；同款关联各店呈现、客户需求及制作成果；不预设固定主推款 |
| 客户 | 去哪里找合适买家、为什么值得联系、怎样推进到订单？ | 研究候选→判断适配→进入商机；商机内看公司、联系人、往来、需求、选款、报价、样品与下一动作 | 研究保留来源，候选不等于客户；发送、回复和采购推进分开记录；订单与履约沿原客户业务接续 |
| 渠道 | 哪个渠道或店铺的问题值得投入、该改哪里、改后有没有用？ | Alibaba看商品承接与询盘；网站看页面、搜索、来源与询盘；抖店按店看商品、内容、成交、发货和售后 | 带日期/统计窗的数据关联具体商品、内容与客户；问题→改动→执行→反馈；国内外价格与履约口径分别维护 |
| 创作 | 做什么内容、有哪些素材、哪个版本能交付？ | 项目内简报、参考板、分镜、生成、剪辑交接及作品预览；独立创作和商品内容分别组织 | 商品内容关联用途与渠道；独立作品按自身标准验收。画布只是一种视图，版本和源文件都能继续使用 |

商品、客户和创作资料直接归入对应对象；客户资料包按需组合对外材料，不复制商品或客户档案。列表突出业务摘要、分类、日期与下一步，追溯细节放在需要时查看的位置。

客户与履约覆盖业务全程，但不立即自建完整ERP。先接现有订单、样品、发货和售后记录；核价、库存或财务能力按真实业务缺口扩展。

## 必须打通的日常体验

**接到询盘。** 总览打开需求及往来；Agent按真实供货资料准备选款和回复，集中列出缺口；在同一客户页面修改正文、看附件、完成已授权发送；结果和下一动作回原商机。不复制背景、不重新建客户、不为一封回复强建项目。

**改善商品。** 从渠道问题或搜索打开商品，查看图片、字段、统计依据和买家疑问；Agent结合研究、文案和素材工具产出可编辑方案；已授权变更提交后读回正式结果并更新原档案。后续数据回到该改动旁，判断是否继续。标题修改只是其中一个动作。

**主动开发买家。** 明确客群与供货适配→选择研究渠道→看候选证据和联系入口→筛出值得推进的公司→组合商品与针对性提案→触达跟进→回收采购信号。海关、Google、社媒和地图是研究来源，不各建客户库；渠道依据实际发现质量调整。

**制作内容。** 从商品或独立创作发起制作；选现有素材，Agent生成分镜与方案，用户看图、改镜头、选版本；生成和剪辑调用现有专业工具，结果回作品并可用于渠道。输入输出关系有含义，取消装饰连线。

**跨对话接续。** 商品优化与独立作品可并行；总览显示谁在做什么、已有成果和下一步。新对话从同一对象接续，不翻旧聊天。会话只是过程，成果属于业务对象；不能声称现有桌面所有聊天已自动接入。

## 共用底座怎样重构

沿用本地服务与SQLite，做一个可维护的应用，不拆微服务，不为重构再购云资源。网站继续在线收询盘，本地连接它的原记录；本机关机时本地任务暂停，官网继续运行。

1. **对象明确，不把所有东西叫项目。** 产品、供货来源、渠道商品、公司/联系人、商机/询盘、订单、内容项目、素材、任务和成果分别有身份及关联；已有ID复用。项目组织持续投入的复杂目标，查询订单和修改商品无需先建项目。
2. **每份事实一个写入位置。** 产品JSON、项目文件和客户源先原位访问；本地数据库存索引、关系、工作状态和会话。网站询盘仍在原后端，本地经接口操作。迁移一类数据时替换旧写入口，不让文件和数据库长期竞争权威。
3. **界面和Agent共用业务动作。** 从找商品、读客户、取素材、保存方案、渠道变更、登记结果等具体动作起步；HTTP供界面，CLI或MCP供Agent，调用同一实现，复用现有客户端。不先造通用插件平台或任意流程编排器。
4. **改造实际执行器。** 移除所有任务只能改一篇Markdown的统一限制；按任务带入对象、关联资料及所需工具，完成真实整理、研究、制作和经营动作。成果可以是可打开的文件、字段修改、选款单或制作对象，文档差异只是其中一种。
5. **工作状态跟随执行事实。** 排队、进行中、需要输入、完成、失败及取消；显示实际步骤和产物，不编造进度百分比。独立对象并行，同一对象写入沿现有协作机制；不另造手工任务台账。普通本地编辑直接保存，可恢复前版；外发、发布及付费按具体动作的已有授权处理。
6. **自动更新承担重复劳动。** 文件变化更新索引，已接平台按接口能力增量刷新，提交后自动读回，新询盘关联待处理工作。页面标来源和上次成功更新；固定同步用程序，研究判断用Agent；通知突出需行动变化，先实现明确触发，不先做复杂自动化画布。

## 保留、替换和不做什么

保留：产品/客户/创作原件、有效渠道客户端、媒体播放底座、CLI运行与事件记录、网站服务。这些可复用，不因界面重构重写。

替换：接口式导航、手填路径主流程、独立空白画布、单文档提案作为通用执行器、人工搬运结果、用技术运行成功代替业务完成、首页堆重复愿景和能力说明。

暂不做：自建完整CRM/ERP/剪辑器、所有数据立即迁库、全渠道自动发信发布、复杂权限体系、无法读取时伪造Codex额度。账号连接、可读用量及失败原因放设置。

## 按完整交付推进

| 顺序 | 交付范围 | 必须亲自走通的完成依据 |
| --- | --- | --- |
| 第一包：统一入口与真实执行 | 总览、全局查找、商品/客户详情、共用任务与成果；接原文件及网站询盘；Agent调用所需工具 | 真实商品→事实/素材→可编辑选款资料；真实询盘→客户与商品→有依据的回复草稿→保存原业务；关闭后可接续。无需为了验收实际外发，不用假数据替代 |
| 第二包：经营与内容贯通 | 完整商品修改、客户研究跟进、素材选择、内容项目与成熟画布 | 商品改动从诊断到渠道结果；制作从简报到可编辑分镜/作品；成果可直接用于客户提案或渠道 |
| 第三包：持续更新与反馈 | 渠道刷新、索引更新、事件触发、报价样品订单接续、改动后反馈 | 新询盘进入待办；实际改动自动回带结果；负责人看到什么值得继续及其依据；逐连接器显示真实覆盖范围 |

主办负责全局取舍和日常使用验收；Sol按业务服务、界面、执行器/连接器并行。开发前约定共用对象与动作，合并后走完整旅程，不各造状态与命名。第一包只开放已走通入口，未做模块不放空壳菜单。

验收看：不用输入路径/平台ID，不重复讲背景，找到真实资料，直接使用成果，知道谁在推进并能继续原工作。代码测试用于正确性，是否减少真实劳动要亲自体验，不能用代码量、接口数或测试数代替。


## 客户开发工作台与多窗口协作（2026-11-06）

### 产品目标

优先解决当前客户开发的人工瓶颈：负责人不应逐个客户要求 Agent 搜索、研究、写信，再等待、逐篇检查和反复解释修改。工作台应能基于明确客群和供货范围，形成一批有证据的合格客户及个性化开发草稿，让负责人集中审查；需要修改时可在该客户上下文内直接交代，修改后回到同一审查队列。客户开发质量、可追溯性和发件信誉优先于单纯发送数量。

### 客户来源与证据

复用现有 prospect/customer 对象和原候选池，不另建名单库。每个候选保留：
- 发现渠道和原始来源记录：如海关/贸易数据、Alibaba 店铺或 RFQ、企业官网、LinkedIn、公开目录、展会或转介绍；具体来源按实际证据记录，不将 Google 搜索结果、网站访客或历史贸易记录互相冒充。
- 公司身份与网站、市场、主营品类、销售渠道、采购线索、联系人及邮箱；每项事实尽可能带来源 URL、观察时间和证据摘录。
- 联系方式状态：原文公开、第三方目录、已验证可收信、退信、未知；禁止从姓名/域名猜测邮箱并标成已核实。
- 资格判断：与贝强供货及目标鞋类的匹配、批量采购可能、合作切入点、缺失证据和不确定性。评分仅用于排序，不代表客户采购意向。
- 去重与抑制状态：同公司/同联系人合并需有可靠身份依据；退订、明确拒绝、投诉、无效地址和禁止联系记录必须在任何批次生成及发送前过滤。

客户详情页按需呈现证据与历史，不把整套研究和所有邮件默认塞进列表上下文。来源不明、身份歧义或联系方式未经核实的候选应显式标注，不进入高置信发送队列。

### 批量研究与开发信审查

工作台提供一个“客户开发批次”视图，但批次是现有客户对象的集合和执行状态，不是第二套 CRM。Agent 可按目标市场、买家类型、产品方向、采购证据、渠道和时间范围发现候选；负责人可指定边界，也可让 Agent 提出客群假设。每个候选先去重、核身份、核来源，再决定是否值得开发。

对合格客户，Agent 逐个生成个性化材料：
- 客户背景与值得联系的具体理由；
- 数据来源、URL、观察日期、事实与推断分开；
- 贝强匹配产品及选款理由，供货事实须回读商品中心；
- 英文主题和正文、完整中文对照；
- 收件人、联系方式来源与验证状态；
- 适合该客户的产品资料附件及实际文件版本；
- 推荐下一步和主要不确定性。

不允许仅替换公司名称的伪个性化模板。证据不足时应降低优先级或退回研究，不为了凑数量生成低质量邮件。

### 集中审核与局部修改

审查列表以“一家公司/一封待发邮件”为行，显示最必要的信息：公司与国家、客户类型、发现渠道、匹配产品、联系地址及验证状态、个性化理由、草稿状态、历史触达次数和下一动作。

点击行后打开侧栏或详情，不离开批次即可查看：
1. 客户背景及来源证据；
2. 推荐产品与依据；
3. 英文邮件及中文对照；
4. 实际附件；
5. 与客户历史往来——按时间区分客户来信、我方已发送回复、自动回复/退信；支持中文译文和 Gmail 原文链接；
6. 历史开发记录、拒绝/退订/跟进状态。

支持按客户逐篇修改、重新生成局部内容、保存版本和标记“通过/需修改/暂缓/不联系”。修改意见只作用于当前客户；经负责人确认的通用经验可以另行提炼，但不得把单客户特例自动推广到全部客户。批次列表应保留筛选和审查进度，多个客户可以连续审查，无需每次打开一个独立 Codex 对话。

### 发送、跟进与结果回写

发送前逐条检查收件人、主题、正文、附件、来源、抑制状态和授权。支持对已逐篇审核的邮件进行明确的批次发送确认：发送前再次展示收件人数量与地址清单；逐封记录 Gmail draft ID、发送结果、时间、Message-ID、退信/回复状态。部分成功时只继续未发送且结果明确的项目；发送结果未知时先对账，禁止盲目重发。批次发送不得绕过现行逐封内容审核要求。

发送后把实际邮件关联回原客户对象；同步客户回复、我方回复、退信、退订、拒绝、询价、选款、报价、样品和订单阶段。后续 Agent 研究应读取相关历史，但只加载与本次决策有关的消息和摘要，原文可追溯。不得把“无回复”自动解释为客户无需求或邮件内容差。

### 日日产能目标与质量门槛

负责人希望逐步达到每天约 100 封精准开发邮件。该数字是待验证的运营产能目标，不是立即将现有邮箱发送量提高到 100 封的指令，也不是系统必须凑满的配额。先分别统计每日发现数、合格客户数、可核实联系人、完成个性化草稿数、负责人审查数、实际发送数、退信/投诉/退订及有效回复。

先验证“每日能准备约 100 份高质量、可审核草稿”的能力，再根据邮箱提供商规则、域名认证、历史送达与退信、投诉、目标国家法律及实际授权，逐步确定可持续发送量。不能通过轮换账号、隐藏发件身份或绕过限额追求数量。新发件域名/邮箱先核验 SPF、DKIM、DMARC、发件身份和回复处理能力；营销类邮件需按适用法规提供有效退出机制并维护抑制名单。不同国家/地区的 B2B 电子营销规则需按目标市场核实，不能把美国规则直接套用全球。

### 多窗口与全局任务派发

工作台应提供全局任务入口：负责人用一句话交代一个跨业务目标，系统把它变成可追踪的父任务，并按业务对象和允许的写入范围创建子任务。子任务可以由独立 Worker Session 执行，完成后回到父任务汇总；无关任务可并行，只有共享同一数据/素材/外部对象时才协调写入。

每个窗口有独立的当前目标、对话、草稿和任务进度，但可通过商品/客户/内容对象 ID 共享事实与成果。窗口关闭不取消后台任务；重新打开能看到进度、结果和下一步。一个任务等待或失败，不应阻塞其他窗口的独立工作。

现有 Codex 聊天窗口不是天然共享上下文，也不能假设工作台能直接向任意已打开的聊天线程注入消息。第一阶段以工作台自己的父任务/子任务和 Worker Session 实现“一句话分发”；现有 Codex 对话作为人工入口，通过 GitHub 和原业务对象接续。只有在实际验证可控的 Codex App Server/session API 后，才考虑把特定受管会话纳入派发，不把普通聊天窗口伪装成已接入 Worker。

### 当前实现与验收边界

当前工作台已具备客户对象、候选发现、客户分析、Gmail 历史读取/翻译、单客户草稿编辑、逐封审核发送、邮件事件关联 Agent Job，以及客户数据版本保护。现有邮件编辑器按单个 object_id 打开草稿；当前没有完整的批量开发批次、集中审查队列、逐篇修改后批次发送和跨对话父子任务派发。因此上述内容是增量产品目标，不应在 README 中标记为已完成。

首个业务验收应从现有候选和客户档案出发，真实走通一批客户：发现与去重 → 证据核实 → 产品匹配 → 个性化草稿 → 集中审核与修改 → 明确确认发送 → 记录真实发送及后续回复。先用一小批校准质量，再扩大每日草稿和发送规模；以客户匹配准确性、材料可审查性、人工审查时间、退信/投诉、有效回复和采购推进评估，而不是以发送数量单独验收。
