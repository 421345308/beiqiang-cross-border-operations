这里维护跨渠道共用的产品身份与供应关系。日常查款打开[产品与渠道查询](产品与渠道查询.html)；采购扩品看[外部供应商扩品](外部供应商扩品.md)。

| 要解决的问题 | 唯一维护位置 |
| --- | --- |
| 是哪一款鞋、当前型号、旧编码、原始资产 | [产品数据](数据/产品.json)；真实原件仍在产品资产目录 |
| 谁供货、供应商原货号、采购入口、采用或候选关系 | [供应来源](数据/供应来源.json)；产品通过来源ID关联，不把供应商变成独立商品系列 |
| 国际站哪些商品对应这款、各自字段与验收怎样 | [国际站商品数据](../../02_Alibaba运营/05_扩品工程/数据/国际站商品.json)、[国际站执行入口](../../02_Alibaba运营/05_扩品工程/国际站合规扩品工程总控.md) |
| 抖店哪家店经营哪款、常规还是加绒 | [店铺与产品对应](../../09_国内电商/抖店/数据/渠道产品对应.json)、[抖店经营入口](../../09_国内电商/抖店/README.md)；具体价格、SKU、审核和履约留该店档案 |

供应商、供货方式、穿着用途、平台类目、店内分组、渠道和店铺是不同维度。按这些属性查询，不因其中一个变化重复建产品、搬媒体或复制一整套项目。平台类目和店内分组在渠道数据维护；共用产品只保留本身的分类与证据。

查询页是派生视图，不是第四份台账。商品ID数不等于款数，历史登记不等于当前在售；尚未关联的渠道不解释为未上架。抖店当前对应覆盖旧店15款和品牌新店28款档案，新店另有9212独立款未补对应。ZX9002、ZX9507、H7212的共用身份仍待核，不因9002/9002-1、7212/H7212近似直接合并；不同款的复古链接也不能仅因889合入M889。

## 为什么这样整合

此前以“HR改造”“路崎全分类”“原四款新增八款”等任务过程组织当前资料；共用台账又位于国际站扩品目录。结果是供应商、真实产品、旧链接整改和渠道经营混在一起，过期暂停、旧人数分工和旧进度也容易被继续执行。现在将来源与产品独立，渠道通过产品ID引用；历史HR编码仅用于定位原商品与替换关系，路崎保留其真实供应商名称、原货号和采购地址。既有BQ编码保持稳定，不为目录整齐重新编号。

当时保留存量商品ID，是为保护已有流量、SKU和订单关联；这解释了为什么一款仍可能关联多条历史链接，不能机械理解成以后必须保留每个重复链接。是否保留、关闭或重新分配，按当前经营价值、平台约束和真实产品证据决策。

早期存在概念图上线但无实际货源的问题，因此增加了真实来源核对。这个原因仍有效；旧HR表中的价格加成、999填报、图数、评分及任务授权不在这里继续固化，具体执行回到当前渠道SOP。HR001旧9002、HR021早期HOLD、26个待分配等均是当时快照，不能由它们覆盖后续正式证据。

来源采用、自产能力、平台审核和买家呈现曾被混为“完成”，因此现在分别留证。接入工厂图、平台评分通过、来源网页可访问都只证明各自范围。外采转自产仍须明确确认；新增渠道不会自动继承另一渠道的材料、价格、库存或履约。

这些理由用于理解取舍。需要重新决策时，先检查当时的问题是否仍存在，再按当前证据选择，不把旧方案永久化。正式请求、回读、原始包和仍能解释弃选原因的证据保留在原位置；被当前数据取代的总控、重复规则和执行队列直接删除，普通修改历史由Git追溯。

## 维护与校验

共用事实改产品或来源；店铺商品改所属渠道。跨域变更只同步实际受影响的记录。先运行 `build_product_workspace.py` 生成国际站视图，再运行 `build_product_hub.py` 生成跨渠道视图；两者均支持 `--check`。脚本在 `08_工具链/06_工作区维护/`。

既有国际站工具通过 `product_registry.py` 组合读取三个数据域并按职责写回，不再写一份混合JSON。新工具直接读取所需数据域。兼容层不接管抖店，不生成副本，检测到其他任务已改数据时拒绝覆盖，重新读取后再处理。
