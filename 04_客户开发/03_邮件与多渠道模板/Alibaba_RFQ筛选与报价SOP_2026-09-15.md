# Alibaba RFQ 筛选与报价 SOP

原建2026-09-15；现行修订2026-10-09（Asia/Shanghai）。岗位、定时配置和经验入口见[RFQ专岗](../07_RFQ专岗/README.md)。本文件是唯一RFQ执行规则；商品事实及商业基线仍以根AGENTS、[商品SOP](../../02_Alibaba运营/00_运营SOP/国际站商品全生命周期SOP.md)和单款证据为准。

## 1. 授权与目标

负责人2026-10-09明确要求专人持续做RFQ、一天查询两次，认为有合适的可以发布。因此符合本SOP的具体RFQ可直接提交供应商报价，不再逐条请求审批；先核验并记录具体需求、SKU、来源、价格/条款和拟发正文。写作任务本身仍不产生外发授权，本专岗的执行授权来自上述明确指令。

范围仅限贝强阿里巴巴国际站RFQ：发现、筛选、对匹配需求报价及报价内必要澄清、回读和记录。不得推导购买报价权益、广告预算、外部渠道群发、供应商付款、签约或信保订单创建的授权。既有有效授权持续适用，直到负责人调整；技术故障不自动撤销授权。

目标是有效采购沟通以及规格、样品、订单推进，不以用完权益或提高报价数量为目标。

负责人2026-10-13明确：选款先按买家用途和需求找合适鞋款，不局限于自有工厂或已有目录；只要对应真实鞋及有效供货入口可评估报价。自产与外采如实内部记录，外采不宣称自产，具体定制、数量、价格与交期仍逐单核验。

## 2. 每次查询

1. 读专岗运行记录、台账、历史正式报价与当前商品证据路由；先处理提交结果未知的记录和待处理买家回复。
2. 发现当前受支持的官方RFQ接口/连接器；无合适能力时使用已读Browser Skill的正常平台页面。既有商品API不能代替RFQ API，不猜接口，不恢复已废止Workctl路线。历史可用网页为 `https://sourcing.alibaba.com/rfq/rfq_search_list.htm`，实际导航和表单以当前页面为准。
3. 记录当前账号报价权益、相关需求剩余席位及观测时间；不采用历史余额。先看自上次成功巡检以来的新增，初次优先最近24小时；中断恢复覆盖漏检窗口，量大时分段处理并记录未覆盖范围，不硬截成“已全查”。
4. 按真实供给选择检索词：walking shoes、casual shoes、slip on shoes、mesh lace up shoes、lightweight shoes、private label shoes；wide toe box仅匹配有证据的SKU。按最新时间查重并结合平台推荐，不机械把全部关键词每次重复扫完。
5. 打开有希望的完整详情：RFQ ID/链接、发布时间/平台时区、买家采购画像、产品参考图、数量及单位、尺码色码、材料/结构、定制包装、目标价、目的地、交期、贸易条款和报价席位。事实与推断分开，缺失写未知。
6. 跨关键词按RFQ ID去重；同买家重复或近似需求合并判断，报价前检查台账、历史正式记录及平台报价管理。历史已提交不能因新台账为空再发。

## 3. 筛选与判定

逐条解释产品/货源吻合度、商业可行性、需求清晰度、采购阶段、时效/席位和可推进的下一步。使用高/中/低优先级和具体理由，不编造官方排名或用内部总分覆盖事实缺口。

| 判定 | 条件 | 动作 |
| --- | --- | --- |
| `QUOTE` | 真实SKU可对应必需规格，报价条件有当前依据，需求/权益有效，内容可兑现 | 核对后直接提交具体报价并回读 |
| `CLARIFY` | 有现实匹配可能，少数关键输入缺失，买家可能接受明确说明的替代款 | 如平台支持独立澄清或有真实依据的条件式报价，提出1–2个关键问题；必填价格缺依据时留待核，不填虚价占位 |
| `HOLD_SOURCE` | 没有对应实鞋或有效采购入口 | 补来源，不提交声称可供的报价 |
| `HOLD_TECH` / `HOLD_TERMS` | 本款关键技术或报价/交期/物流条件待核 | 只处理缺口，其他合格RFQ继续 |
| `SKIP` / `SKIP_RISK` | 明确不匹配、失效、重复首报、拒绝联系、品牌仿制或条件不可满足 | 记录理由，不消耗权益 |

自有工厂身份须映射原始包；外采真实鞋有有效采购入口可内部确认供货能力，不能宣称贝强自产，也不能据采购入口承诺具体库存、固定价或交期。平台库存不是实物库存。

不以国家、认证标签或数量单独决定优先级。一双可能是样品测试，小单定制需核可行性；大单描述混乱仍需澄清。买家历史不足是待验证信息，不等同虚假。

要求医疗/矫形、安全防护、认证、防水/防滑等级及实验室性能时核单款证据；硬度、密度、回弹、stack height、drop、楦型、新模具、NDA和保密tech pack按[技术型品牌买家SOP](../../07_知识库与Skills/01_运营SOP/技术型品牌买家询盘评估SOP.md)评估，区分买家目标、已确认能力、固定不可调项和打样后实际结果。不承诺尚未具备的能力。

## 4. 报价核验

- 对准具体款式和买家必需规格，只推少量匹配实款，替代款明确差异。真实图/平台商品与当前款一致，不用生成图证明实物。
- 价格依据具体数量档、币种/单位、款式材料、尺码配比、色码、Logo、包装和贸易条件。读当前商品SOP及单款核价，不复制历史RFQ价格或把店铺展示价当本单已核价；FOB目标区间不构成统一报价。
- 条件未齐可给有依据、清楚列明适用条件的参考报价；最终价需本单复核。平台必须填固定数字而无可兑现依据时，不能虚填最低价或零价。
- 成本加价与实际费用分开；包含/不含运费税费、报价有效期和未确认事项清楚写。有效期影响供方价格或交期时须有支持，不编造保价承诺。
- 样品存在、费用及周期、现货数量和固定交期逐单核验。不把填报基线解释成已实测包装或统一发货承诺。DDP/FBA需目的地、实际箱规/重量、数量、路线和时效后独立核算。
- 内部来源、成本、供应商、来源平台和风控标签只留内部；未证实单款自产/OEM能力时不写工厂直供或已能定制，可请买家提供要求后核实。
- 首答按项目 `rfq-quote-assistant` 写，回应需求、说明匹配与差异、给报价条件/待核点，再给具体下一步；不照搬泛化长模板。

## 5. 提交、去重与回读

1. 保存精确RFQ、匹配SKU/商品ID、来源与核价证据、币种/单位/数量/条件、完整拟发正文和附件，以及检查时间。台账先写 `PREPARED`。
2. 最后核当前权益、席位、未过期及未首报；有同一RFQ的 `SUBMITTING`、`SUBMIT_UNKNOWN` 或 `SUBMITTED` 先处理已有记录。将本次状态写 `SUBMITTING` 后执行正常平台提交，不批量盲发。
3. 成功页、报价管理或官方接口明确回执证明提交后写 `SUBMITTED`、报价单号、时间和权益变化。填写表单、按钮点击或请求发起不算提交成功；网页写入按Browser要求保存结果截图。
4. 失败写平台业务错误/技术故障及影响范围。结果未知写 `SUBMIT_UNKNOWN`，先查报价管理/官方回读，未核对前不重复提交。平台安全拒绝或安全服务异常不通过其他控制通道绕行。
5. 记录买家人工回复和下一动作，自动回复与采购回复分开。后续同买家沟通/订单按适用的既有授权和专项SOP推进，不扩展外部渠道或订单承诺。

## 6. 台账与复盘

[RFQ台账](../07_RFQ专岗/RFQ台账.json)按 `rfq_id` 保存唯一记录，按实际填写：链接/买家与需求原文、发布时间及时区、首次/最近观察时间、匹配SKU、事实/核价证据及核对日、优先级/理由、判定/待核项、拟发/实际正文、报价条件、提交状态与尝试记录、报价单号/回执路径、权益观察、买家反馈、下一动作/时间与停止联系状态。未知数据写null/未知，不生成假ID。调整报价保留原正式回执与新变更范围。

巡检记录另写开始/结束时间、真实检索词、覆盖窗口、结果计数、故障和待补范围。访问失败是“未完成检查”，不能记为“无合适”。

每周在正常巡检中核查提交→人工回复→有效采购沟通→样品/订单讨论，保存个案与分母。经验写入[理论与经验](../07_RFQ专岗/理论与经验.md)，保留日期、来源、范围、其他解释和反例，不自动晋级长期记忆。

无合适机会或状态未变时保持安静；提交成功、有效采购进展和需要负责人操作的故障才通知。故障通知说明已证实原因、正常处理、精确影响与最小必要动作，同一未变故障不反复提醒。
